# Repo navigation

## Find a symbol: grep `.claude/LINE_INDEX.md` first

Auto-generated index of **every `.py` in the workspace**, ~24k lines, format
`L<line> <signature>` grouped under `## <path> (<total lines>)`. Regenerated by
git hooks on commit, checkout, merge and rebase
(`.git/hooks/_run_line_index.sh` → `.vscode/generate_line_index.py`), so it is
current unless you have uncommitted new definitions.

```sh
grep -n "def resolve_fallback" .claude/LINE_INDEX.md
grep -n "^## Core/BuildMgr.py" -A200 .claude/LINE_INDEX.md
```

One search against one file beats ripgrep across ~1,500 files. Use ripgrep for
*call sites* and string content; use LINE_INDEX for *definitions*.

## Which tree owns what

| Tree | `.py` | What it is |
|---|---|---|
| `Core/` | 559 | **The library.** Single Python-facing source of truth |
| `Sources/` | 497 | Per-author contributed scripts — *not* one subsystem (see below) |
| `Widgets/` | 184 | In-client UI, folder-discovered → skill `widget-authoring` |
| `Legacy code and tests/` | 153 | Dead weight. Do not modify, do not cite as precedent |
| `Examples/` | 61 | Reference snippets |
| `HeroAI/` | 52 | Multibox combat/follow engine → skill `heroai-bt-engine` |
| `UI_RE/` | 41 | UI reverse-engineering experiments |
| `Bots/` | 38 | Bot implementations (`marks_coding_corner/` is the user's) |

Inside `Core/`: treat it as the source-of-truth layer,
`py4gwcorelib_src/` as support infrastructure, and `GLOBAL_CACHE` as a
derivative consumer/cache layer. **Prefer module-specific imports over the
`Core` facade** — the facade has import side effects (see hard rules).

### `Sources/` is per-author, not per-feature

`aC_Scripts` (258), `frenkeyLib` (85), `ApoSource` (81), `ZaishenBounty` (35),
`modular_data` (14), then `Nikon_Scripts`, `Sasemoi`, `sch0l0ka`, `oazix`,
`tower_of_courage`, `marks_sources`, `Wick Divinus bots`. There is no shared
architecture across them; do not generalize a pattern found in one.

`frenkeyLib` is the legacy compatibility shim → skill
`reforged-vs-frenkey-primitives`.

### ModularBot — the paths are not where you'd guess

- implementation: `Core/modular/`
- recipes / prebuilts / tests / tools: `dev/reference/modular_data/`
- widget wrappers: `Scripts/py4gw-modular/tools/`

There is **no `dev/reference/modular_bot/`** despite older references to it. The
validator is `dev/reference/modular_data/tools/validate_modular_architecture.py`
(not `validate_modular_docs.py`).

## Entry points

| Purpose | File |
|---|---|
| In-client widget bootstrap | `Py4GW_widget_manager.py` → `dev/legacy/widget_catalog/Py4GW_widget_catalog.py` |
| External launcher / injector | `Py4GW_Launcher.py`, `Py4GW_Reforged_Launcher/` |
| Bridge: injected client | `Scripts/py4gw-devtools/scripts/Tools/Bridge Client.py` |
| Bridge: daemon | `bridge_daemon.py` (widget server `127.0.0.1:47811`, control `47812`) |
| Bridge: operator CLI | `bridge_cli.py` (targets control port `47812`) |
| MCP adapter | `py4gw_mcp_server.py` — stdio→daemon, never straight to injected clients |

MCP exposes a deliberately narrow tool set: `list_clients`, `list_namespaces`,
`list_commands`, `describe_runtime`, `get_map_state`, `get_player_state`,
`list_agents`. It is not a generic bridge-call passthrough.

## Docs hierarchy — 48 files, several dead

**Authoritative:**

- `docs/Py4GW_Conceptual_Model.md` — canonical architecture and terminology
- `docs/widget_manager_and_catalog.md` — before any widget-discovery change
- `docs/RE/reverse_engineering_reference.md` — RE entry point
- `dev/bridge/runtime/README.md` — bridge/daemon operator reference
- `docs/persistence_jail/` — persistence audit and rationale

**Secondary / derived:**

- `docs/MCP_bridge.md` — bridge *planning*, not primary architecture
- `docs/Py4GW_Model_Features_Detail.txt` — derived plain-text export, scanning only

**Dead or superseded — do not follow:**

- `docs/ImGui_Facade_Migration_Plan.md` — the `ImGuiRuntime` rebuild was
  abandoned and deleted. `Core.ImGui` is the only wrapper.
- `docs/buildmgr_retirement_blueprint.md` — superseded by
  `docs/heroai_bt_migration_complete.md`; §1–2 analysis still accurate
- the `IniManager_*` / `Configparser_To_Settings_*` plan series — completed
  migrations, kept as precedent for conversions

**Handover docs live at repo root**, not in `docs/`:
`FOLLOW_REFACTOR_HANDOVER.md` (read before touching follow-system code),
`DBMGR_HANDOVER.md`.

## Branch scratchpads

`.claude/branch_status/<branch-name>.md` — per-branch record of scope, what is
core-lib-worthy vs local, PR split plan, followups. Check for one matching the
current branch before planning work; keep it updated. → skill `pr-workflow`.

## Shell and interpreter

In `.claude/context/hard-rules.md`, always loaded. Short version: use
`.venv/Scripts/python.exe` (3.13.0 32-bit), the Bash tool is Git Bash rooted at
the repo, PowerShell is 5.1 with no `&&`, and filenames contain spaces and `&`.
